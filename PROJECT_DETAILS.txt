1. EXECUTIVE SUMMARY & ARCHITECTURAL OVERVIEW
================================================================================
Meridian Diagnostics (lab-lims) is a modern, high-performance web frontend
engineered for clinical diagnostic laboratories, pathology centers, and hospital
diagnostic wings. 

Key Architectural Highlights:
1. Complete Separation of Concerns (Frontend-Backend Decoupling):
   - Designed strictly as a client-side interface that mirrors an exact relational
     DBMS schema.
   - Built around an architectural "Seam" (`src/services/http.ts`). All data access
     flows through standard service methods that either communicate with an in-memory
     mock database or issue real REST calls against `VITE_API_BASE_URL`.
   - Switching between mock data and the live production backend requires changing
     a single environment variable (`VITE_API_MODE=live`), with zero changes to
     components, hooks, or state logic.

2. Strict Database-First Schema Alignment:
   - Field names directly match the SQL database schema (`Patient_ID`, `Test_ID`,
     `Order_ID`, `Sample_No`, `Report_ID`, `Staff_ID`, `Lab_ID`, `Doctor_ID`).
   - Prevents impedance mismatch when connecting to the relational backend.

3. Role-Driven Clinical Workflows:
   - Accommodates five operational divisions across four distinct user roles:
     Patients, Lab Technicians, Pathologists, and System Administrators.
   - Built with role-specific landing workspaces, granular permission route guards,
     and contextual clinical actions.

4. Production-Grade UX & Accessibility:
   - WCAG AA compliant contrast in both Light and Dark themes.
   - Multi-channel communication (color is never used alone; accompanied by text
     labels, symbols, and directional indicators).
   - Zero-dependency PDF generation leveraging browser print stylesheets and A4
     clinical report layout.

4. DATABASE SCHEMA & DOMAIN DATA MODELS (DBMS MAPPING)
================================================================================
The application types mirror the relational database schema exactly:

1. Patient & Patient_Contact
   - Table `Patient`: `Patient_ID` (PK), `First_Name`, `Last_Name`, `DOB`, `Gender` ('M' | 'F' | 'O')
   - Table `Patient_Contact`: `Patient_ID` (FK), `Contact_No` (Regex: `^[6-9]\d{9}$`)

2. Test (Generalization / Specialization)
   - Table `Test`: `Test_ID` (PK), `Test_Name`, `Test_Category` ('Pathology' | 'Radiology'), `Price` (INR), `Unit`
   - Specialization `PathologyTest`: carries `Specimen_Type` ('Blood', 'Serum', 'Urine', 'Tissue', 'Stool', 'Swab')
   - Specialization `RadiologyTest`: carries `Imaging_Modality` ('X-Ray', 'MRI', 'CT Scan', 'Ultrasound', 'Mammography')

3. Doctor (Referring Physician)
   - Table `Doctor`: `Doctor_ID` (PK), `Doctor_Name`, `Specialization`

4. TestOrder & OrderIncludesTest
   - Table `TestOrder`: `Order_ID` (PK), `Order_Date`, `Patient_ID` (FK), `Doctor_ID` (FK),
     `Status` ('Pending' | 'Processing' | 'Completed' | 'Cancelled'), `Total_Price`
   - Table `OrderIncludesTest`: `Order_ID` (FK), `Test_ID` (FK)

5. Laboratory (Facility)
   - Table `Laboratory`: `Lab_ID` (PK), `Lab_Name`, `Location`, `Contact_No`

6. LabStaff (ISA Hierarchy)
   - Table `LabStaff`: `Staff_ID` (PK), `Staff_Name`, `Shift` ('Morning' | 'Evening' | 'Night' | 'General'), `Staff_Role`
   - Subtype `LabTechnician`: `Tech_ID` (Shared PK/FK), `Certification`
   - Subtype `Pathologist`: `Pathologist_ID` (Shared PK/FK), `License_No`, `Qualification`

7. Sample (Specimen Collection)
   - Table `Sample`: `Sample_No` (Per-order sequence: S1, S2...), `Order_ID` (FK), `Patient_ID` (FK),
     `Sample_Type`, `Collection_DateTime`, `Lab_ID` (FK), `Tech_ID` (FK),
     `Status` ('Collected' | 'In Transit' | 'Received' | 'Rejected')

8. Report & HasResult
   - Table `Report`: `Report_ID` (PK), `Order_ID` (FK), `Report_Date` (Nullable while draft),
     `Patient_ID` (FK), `Doctor_ID` (FK), `Pathologist_ID` (FK)
   - Table `HasResult`: `Report_ID` (FK), `Test_ID` (FK), `Observed_Value` (string to support '<0.01' or '>1000'),
     `Unit`, `Remark` ('Normal' | 'Elevated' | 'Critical')

5. SYSTEM ROLES, PERMISSIONS & WORKSPACES
================================================================================
The application is governed by 4 distinct roles and 11 granular permissions:

Granular Permissions:
  - `patient:read`, `patient:write`
  - `catalogue:read`, `catalogue:write`
  - `order:read`, `order:create`
  - `sample:read`, `sample:write`
  - `report:read`, `report:write`
  - `staff:manage`

Role Matrix:
1. Administrator (`admin`)
   - Permissions: Full access to all 11 permissions.
   - Dedicated Workspace (`/admin`): Complete operational dashboard featuring
     live patient counts, order pipeline status, booked revenue metrics, sample
     status distribution, and diagnostic findings breakdown.
   - Quick administrative actions: Register patient, add staff, add laboratory,
     manage test catalogue.

2. Patient (`patient`)
   - Permissions: `catalogue:read`, `order:read`, `order:create`, `report:read`
   - Dedicated Workspace (`/patient`): "My Health Record" portal strictly scoped to
     the logged-in patient's `Patient_ID`.
   - Features: View past orders, track live sample progress, access and download/print
     final diagnostic reports, book new tests self-service.
   - Security Boundary: Prevented from accessing the global patient directory or
     other patients' records via `usePatientScope`.

3. Lab Technician (`technician`)
   - Permissions: `patient:read`, `catalogue:read`, `order:read`, `sample:read`, `sample:write`
   - Dedicated Workspace (`/lab-tech`): Sample collection dispatch board.
   - Features: Monitors orders pending sample collection, accessioning interface,
     logs new samples with auto-incrementing IDs (`S1`, `S2`), assigns samples to
     laboratories, tracks delivery status.

4. Pathologist (`pathologist`)
   - Permissions: `patient:read`, `catalogue:read`, `order:read`, `sample:read`, `report:read`, `report:write`
   - Dedicated Workspace (`/pathologist`): Clinical diagnostic workbench.
   - Features: Pending review queue of orders with collected specimens, tabular
     result entry, clinical remark assignment, electronic authorization and report
     issuance.

6. CORE FUNCTIONAL MODULES & FEATURES
================================================================================

MODULE 1: PATIENT & ORDER MANAGEMENT
------------------------------------
- Patient Directory (`/patients`): Search by name, MRN/Patient_ID, or mobile number;
  filter by gender; sort by name or order history; pagination (12/page); row actions
  to edit or delete (with foreign key checks).
- Patient Registration (`/patients/new`): 3-step interactive wizard using Stepper
  (Step 1: Name, DOB, Gender; Step 2: Dynamic contact numbers list; Step 3: Review
  and confirm).
- Patient Profile (`/patients/:id`): Full patient demographics, emergency contacts,
  and complete historical timeline of test orders and statuses.
- Test Catalogue (`/catalogue`): Browsable grid of diagnostic investigations categorized
  into Pathology and Radiology; displays specimen types or imaging modalities, units,
  and prices; administrator modal to create/update/delete tests.
- Order Booking (`/orders/new`): Real-time interactive ordering interface; searchable
  catalogue with spotlight cards; live shopping cart recalculating order total in INR;
  referring doctor selection; single-click order generation.
- Order Dashboard (`/orders` & `/orders/:id`): Tabbed status filtering (All, Pending,
  Processing, Completed, Cancelled); cancel and delete capabilities; detailed view
  displaying ordered tests, associated samples, and direct report link.

MODULE 2: LAB TECHNICIAN & SAMPLE INTAKE
----------------------------------------
- Sample Intake & Accessioning (`/samples`):
  - Order lookup with auto-population of patient details.
  - Automatic suggestion of sequential sample identifier (`nextSampleNo`: S1, S2...).
  - Selection of sample specimen type (Whole Blood, Serum, Plasma, Urine, Stool, etc.).
  - Intake collection timestamp with validation preventing future timestamps.
  - Assigned laboratory facility and collecting technician.
  - Immediate logging and status updates (`Collected`, `In Transit`, `Received`, `Rejected`).
  - Historical sample accession log with pagination and order filtering.

MODULE 3: PATHOLOGIST & RESULT ENTRY
------------------------------------
- Worklist / Result Queue (`/results`):
  - Displays all orders whose samples have been collected and are ready for analysis.
  - Ordered chronologically (oldest collection first) to prioritize turnaround time.
  - Shows patient details, test count, and sample count.
- Result Entry Worksheet (`/results/:reportId`):
  - Dedicated clinical worksheet presenting every test included in the order.
  - Numeric/text observed value input.
  - Standardized units (e.g., mg/dL, g/dL, cells/uL).
  - Pathologist clinical judgement selector: `Normal`, `Elevated`, or `Critical`.
  - Report Authorization: On submission, automatically issues the report, records
    pathologist identity and credentials, sets `Report_Date`, and transitions the
    order status to `Completed`.

MODULE 4: REPORT VIEWER & PRINT ENGINE
--------------------------------------
- Report Directory (`/reports`): Searchable directory of issued diagnostic reports
  with summary findings badges (Normal / Elevated / Critical counts).
- Digital Report Viewer (`/reports/:reportId`): High-fidelity clinical report rendering
  hospital letterhead, accreditation numbers (NABL), patient metadata, referring
  doctor, structured test findings table, and pathologist authorization block.
- Zero-Dependency Print Engine (`/reports/:reportId/print`):
  - Renders outside the application shell (no sidebar or top bar).
  - Uses specialized A4 print stylesheet (`src/styles/print.css`).
  - Native browser Print / Save-as-PDF integration with repeated table headers,
    page break protections, and high-contrast clinical print formatting.

MODULE 5: ADMINISTRATION & FACILITY MANAGEMENT
----------------------------------------------
- Staff Directory (`/admin/staff`):
  - Tabbed viewing by staff role: All, Technician, Pathologist.
  - Displays work shifts (Morning, Evening, Night, General).
  - Dynamic Staff Form Dialog: Automatically toggles specialization fields
    (Certification for Technicians; License No and Qualification for Pathologists).
  - Conflict-safe deletion (refuses deletion if staff is tied to samples or reports).
- Laboratory Locations (`/admin/labs`):
  - Manages processing facilities across regions.
  - Tracks facility name, physical location, and contact numbers.
  - Create, update, and delete laboratory facilities.
- Operational Analytics:
  - System-wide KPIs: Total registered patients, active tests, staff count, facilities count.
  - Order pipeline status breakdown bar.
  - 7-day order booking volume and booked revenue in INR.
  - Sample pipeline status breakdown (Collected, In Transit, Received, Rejected).
  - Clinical findings distribution (Normal vs Elevated vs Critical).

7. API CONTRACT & SERVICE LAYER (THE INTEGRATION SEAM)
================================================================================
The service layer (`src/services/`) encapsulates all asynchronous communication.
The core engine is `src/services/http.ts`:

```
UI Components -> TanStack Query -> Service Methods -> http.ts -> Mock DB Handler
                                                               -> Live REST API (fetch)
```

Configuration via `.env`:
  - `VITE_API_MODE=mock`: Routes requests to the internal in-memory mock engine.
  - `VITE_API_MODE=live`: Directly issues `fetch()` calls to `VITE_API_BASE_URL`.
  - `VITE_API_BASE_URL=http://localhost:8080/api`: Backend endpoint base.

Endpoints Defined in the Seam:
  - `GET/POST /patients`, `GET/PATCH/DELETE /patients/:id`
  - `GET /doctors`
  - `GET/POST /tests`, `PATCH/DELETE /tests/:id`
  - `GET/POST /orders`, `GET/DELETE /orders/:id`, `PATCH /orders/:id/cancel`
  - `GET/POST /samples`
  - `GET /reports`, `GET /reports/:id`, `GET /pending-results`, `PUT /reports/:id/results`
  - `GET /laboratories`, `POST /laboratories`, `PATCH/DELETE /laboratories/:id`
  - `GET /staff`, `POST /staff`, `PATCH/DELETE /staff/:id`
  - `GET /analytics/summary`
  - `POST /demo/reset`

8. MOCK DATA ENGINE & PERSISTENCE
================================================================================
The project features a deterministic, realistic mock engine:
- Seeded PRNG (`src/mock/rng.ts`): Uses a fixed seed (Lehmer LCG) so that initial
  loads always generate identical, reproducible clinical records.
- Realistic Dataset (`src/mock/seed.ts`):
  - 48 realistic Indian patient profiles with valid phone numbers and birth dates.
  - 12 certified laboratory staff (8 Technicians across shifts, 4 Pathologists).
  - 4 processing laboratory centers across Bengaluru.
  - 8 referring medical doctors spanning 7 specialties.
  - 28 diagnostic tests (Pathology & Radiology) with authentic pricing and units.
  - ~180 test orders spanning 180 days with associated samples and reports.
- State Persistence (`src/mock/db.ts`):
  - Edits made during user sessions (booking orders, collecting samples, entering
    results) persist in `sessionStorage`.
  - A "Reset demo data" action enables restoring pristine factory seed state.
- Simulated Network Conditions (`src/mock/latency.ts`):
  - Injects realistic random latency (180ms to 450ms).
  - Provides hooks to simulate slow connections and server errors for QA testing.

9. DESIGN SYSTEM, UI COMPONENTS & LOCALIZATION
================================================================================
Design Principles:
- Hairline Borders Over Heavy Shadows: Creates clean, dense medical-grade surfaces.
- Multi-Signal Accessibility: Colors are always paired with text or glyphs.
- Clinical Color Tokens (`tokens.css`):
  - Surfaces: Canvas (`#fcfcfd`), Surface (`#ffffff`), Inset (`#f9fafb`), Hairlines (`#e4e7ec`).
  - Accents: Deep clinical blue (`#0b5fa5`).
  - Result Flags: Normal (Muted), Low (Blue), High (Amber), Critical (Crimson).
  - Pipeline Statuses: Pending, Collected, Received, Processing, Completed, Rejected.

UI Primitive Library (21 Components in `src/components/ui/`):
  Button, Input, Select, Checkbox, RadioGroup, Switch, Textarea, Field, Dialog,
  DropdownMenu, Popover, Tabs, Toast, Tooltip, Badge, Skeleton, Spinner, Surface,
  Separator, Kbd, and Table.

Indian Localization Standards (`src/lib/format.ts`):
  - Currency: Indian Rupee (INR - e.g., ₹1,450), zero decimals.
  - Dates: `dd MMM yyyy` (e.g., 14 Mar 2026), never ambiguous numerical dates.
  - Timestamps: `dd MMM yyyy, HH:mm` in 24-hour format.
  - Age: Calculated precisely from DOB (e.g., "34 y" or "8 mo" for infants).
  - Phone Validation: 10-digit mobile starting with 6, 7, 8, or 9.

Local Development:
  1. Clone or navigate to the repository directory:
     cd c:\dbms-diagnostic-lab-frontend
  2. Install dependencies:
     npm install
  3. Launch local Vite development server:
     npm run dev
  4. Access in browser:
     http://localhost:5173

Available Scripts:
  - `npm run dev`: Starts Vite dev server with hot-module reloading.
  - `npm run build`: Executes TypeScript compilation (`tsc -b`) and bundles for production into `dist/`.
  - `npm run preview`: Serves the production build locally with SPA history rewrites.
  - `npm run lint`: Runs fast static code analysis via oxlint.

Connecting to Real Backend:
  Edit `.env` in the project root:
  ```
  VITE_API_MODE=live
  VITE_API_BASE_URL=http://your-backend-host:8080/api
  ```
  No component, service, or configuration code needs to be modified.

Production Deployment Notes:
  - As a single-page application using HTML5 history routing, your production
    web server (Nginx, Caddy, Apache, or AWS S3/CloudFront) must rewrite all
    non-file routes to `/index.html`:
    
    Example Nginx configuration:
    location / {
      try_files $uri $uri/ /index.html;
    }
